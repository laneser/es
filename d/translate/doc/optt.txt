   一個提升 LPC 速度的簡介
 (特別針對 MudOS 0.9.x 與其變化型)

     Written by Luke Mewburn <zak@rmit.edu.au>
     Translated to Chinese by Devianth <davidwu@uclink.berkeley.edu>

     Version: 1.2.1
     Date: 10.30.94

0. 簡介

    我會寫這份文件是因為我發現 LPmud 有走向更複雜, 更玩家化的趨勢。
這不是問題, 問題是 LPC 處理的方式(程式是一段處理完才處理下一段), 寫
得不好的程式會使部份或整個 mud 慢下來。
    所以, 我決定找出最有效率來解決問題的方法並整理出來。我假設讀者有
一些程式設計的經驗, 特別是 C 或是 LPC。 但, 因 driver 越來越不同的趨
勢, 此文件可能無法正確地保證非 MudOS drivers
(例: Amylaar 的3.2@22 driver)。

    在例子中, 假設下列的解釋:
int i, j, max, bitfield;
object *list;
string *arr, name;

    和 C 一樣, LPC 支援 `動態配置' 的概念。也就是說, driver 只會在程式
需要時、才配置記憶體 (用完後除去配置)。和 C 不同的、LPC 會自動除去用完
不用的記憶體配置(當沒有程式指向此資料) - 這叫做`垃圾收集'。字串、矩陣、
和 mapping 都是`動態'處理的。

    雖然動態配置對於結構化程式很有幫助、但它會吃去些 CPU time。此文件的
一個目的就是讓你知道如何有效地利用動態配置。

一. 一般問題

    在我開始介紹各個加速的方法之前、我先提提一些大家所該知道寫程式的
原則。

    第一個是`電腦花 80% 的時間執行 20% 的程式", 又稱為 `80/20'原則 (有時
叫 75/25 或 90/10)。 這個經證實的事實可以有效的幫助你寫 LPC。不要把時間
花在提高每一行程式的效率 - 沒那種時間。集中在幾段執行次數較多的地方像是
FOR 迴圈等等。

    第二點是正確的問題解決方式。經常一個複雜的解決方式其實只需要一個較
簡單的方式。當處理少數的資料時, 一個簡單的方式會比較有效率。但是有時偷
懶的寫程式方式執行時會較慢。

    現在多數的(或全部的) drivers 沒有更高級的 LPC 效率增加方法 (像
re-writing 和 loop strength-reduction 指令) 你還是可以用較聰明的
程式寫法。

    一個好的增效方式是把一段重複執行的程式或函數拿出迴圈外。一個最明顯
的例子就是 w用來做迴圈跳出狀況的 `sizeof(arr)'。其他可能的狀況包括在回
圈每執行一次迴圈中所呼叫一個函數的傳回值都一樣 -- 解決的方法是在迴圈前
先把此函數的傳回值存入一個臨時變數。 例:

for ( i = 0; i < max ; i++)
    if ( list[i] == some_condition )
do_something_with( list[i], this_player()->query("name") );
    
    假設 name 是不變的

name = this_player()->query("name");
for ( i = 0; i < max ; i++)
    if ( list[i] == some_condition )
do_something_with( list[i], name );

    一個固定的和好讀的程式寫法雖然不會加快執行速度, 但可加速 debug
或改程式。不同的人有不同的格式觀念、選一個固定和適合你的寫程式的格
式會有很大的幫助。

2. 資料型別

    LPC 至少有下列資料型別: int(整數), string(字串), object(物件),
mixed(混合), mapping, 還有這些型別的矩陣。一些資料型別的使用摘記:

2.1. INT(整數) 這段我看得懂, 但我翻不出來 :P 

The integer data type is very efficient to use, as no dynamic
allocation required to use it.  By using bitfields (e.g, hand-coded
with #defines, (simulating ANSI c's enum's)), you can store a variety
of flags information as well. This latter use is much faster than
storing information of bit size, as long as you only need 32 bits.
Example code to manipulate integer bit fields follows (assuming that
VALUE is 1, 2, 4, 8, etc):

bitfield |= VALUE;// set bit VALUE
bitfield &= ~VALUE;// reset bit VALUE
bitfield & VALUE// test bit VALUE

If you want to set bit n, replace VALUE with (1 << n).


2.2. STRINGS(字串)

    字串是最常用的資料型別、但它需要動態配置。恆字串(像單純的 'write'
指令) 是被存於一個 "字串表" 、所以重複使用時不需要更多的記憶體。但累
積字串(有 + 記號的)編輯時需要很多 CPU time - 每"加"一段字就要配置記
憶體一次。一個常見的寫程式的方式看起來如下:

write("這是森林\n" +
      "一片無聊斃的森林\n" +
      "你開始想睡覺了。\n");

    好、這個呢, 是最 _壞_ 的寫恆字串的方法 - 編輯時又慢, 又浪費記憶體。
注, 在 MudOS 0.9.15 中, 可以不用寫這個 "+" - 但是結果是相同的, 每加一段
字串、就要動態配置一次記憶體。請用以下的方法:

write("\
這是森林\n\
一片無聊斃的森林\n\
你開始想睡覺了。\n\
");

    這樣子, 字串會被一次全部儲存。在不哽住文字處理的情況下你大約可以寫
下一整頁的文字。將你的文章分段至這個長度, 並用另一個 write 敘述。

    注: 注意, \ 後到 end of line 之間不能有空白號, 文字處理會看不懂。

    更新: 自 MudOS 0.9.14.3 後, 恆字串的設定新加了一個符號 - `@'、所以
    以上可簡化為:

write( @ENDMESSAGE
這是森林
一片無聊斃的森林
你開始想睡覺了。
ENDMESSAGE
);

    (這個 'ENDMESSAGE' 可為任何不出現於文體本身的字串、並且一定要獨立
出現在新的一行裡、不然它不會被當作 'end of message' 的符號。
注亦: 'ENDMESSAGE' 前後都不能有空白號。

    另一個低效率的程式寫法::

write("你的名字是 " + this_player()->query("name") + "\n" +
" 你的等級是 " + this_player()->query("level") + "\n");

    如果你的 driver 支援 printf(), 用以下的寫法:

printf("你的名字是 %s\n 你的等級是 %d\n",
    this_player->query("name"), this_player->query("level") );


    當然還有許許多多類似的情況, 不過你應該懂了吧。

    但是, 別搞錯了, 有時累積字串還是必要的, 所以呢, 不要想盡一些
又長又臭的辦法來回避它 (弄不好, 比累積法更慢)。

2.3. FLOATS(浮點, 就是含小數點的啦)

    在 0.9.5 driver 中, 加入了浮點資料形式。可用 'float' 來宣告(同在
C 裡的 "double" type)

    也有像 cos, sin, (和類似的運算), ln, 和 sqrt (平方根) 的運算函數
。這種資料形式可以在編輯暫時跳過, 但我看不出來有什麼關係。

    浮點的運算比整數慢、所以能用整數運算時儘量不要用浮點運算。需要用
到浮點運算時, 儘量先把它們算出來以迴避重複的運算(這點對於任何程式都通)。

    矩陣是非常有用的, 但是和字串相同, 不當的使用會造成低效率的程式。
    一個在迴圈內有增加或除掉項目的迴圈通常是較慢的。解決的方法是適當
的運用記憶體預先配置。

摘自 TMI-2 的 /adm/daemons/cmd_d.c :

bin_ls = get_dir(path + "/");
result = ({ });
for (i = 0; i < sizeof(bin_ls); i++) {
            if(sscanf(bin_ls[i], "_%s.c", tmp) == 1)
result += ({ tmp });
        }
        cmd_table[path]=result;
    
    這裡, 並不是所有的項目都有"選"到。而是修改過後才放到矩陣中的。
    用下面的方法:

bin_ls = get_dir(path + "/");
i = sizeof(bin_ls);
result = allocate(i);
j = 0;
while (i--) {// see below for why `while' is used
            if(sscanf(bin_ls[i], "_%s.c", tmp) == 1)
               result[j++] = tmp;
        }
        cmd_table[path]=result[0..j-1];

    注亦 sizeof(bin_ls) 是不變的, 然後, 才把需要的項目加入, 最後
才把結果放到適當大小的矩陣中(用 [0..j-1])。

而用 += 的矩陣處理和處理時間增加成 exponential(我不行了)。

2.5. MAPPINGS

    Mapping 就是連接性的矩陣 - 能用基本資料形式(int, string, 或 object)
來做指標的資料結構。以資料結構來說, 它通常比矩陣來的有效率, 並可以用來
模仿 C 裡的`structs'敘述。

    基於 mapping 內部處理的方式, 預先配置的 mapping 比較有效率。這
在你已知道 mapping 項目的多寡約為 x (還可以加)並且不減低於 x 時最為顯
著。(就是說, 使用 map_delete 在一個 x 項目的 mapping 時, 它不會把記憶
體釋放回系統(原作寫得不清不楚))

    一個常見的預先配置方法可在 emote daemon 或像 /std/user (或
/obj/player) 裡的標準物件中找到。對於前者, 如果你已知有約 200 項項目,
不要用下列方法:

emotemap = ([ ]);
    
    改用:

emotemap = allocate_mapping( 200 );



3. CONTROL FLOW & LOOPING (完全不懂 :P)

    在一個完整的 LPC 程式中, 有各種方法來使程式流程的控制(經測試和迴圈
結構的一部份)變得更有效率。

3.1. WHILE

    最簡化的(在簡化程式方面)迴圈方式: 例:

list = users();
for ( i = 0 ; i < sizeof(list) ; i++ )
    do_something_with_item( list[i] );
    
    雖簡化, 但效率不高, 特別是 sizeof(list) 被重複的呼叫, 運算(請
看一般問題)。如果 i 增加的順序有關係, 用下面的方式:

max = sizeof(list);// slight performance gain
i = -1;
while ( ++i < max )//evaluate and increment at same time
    do_something_with_item(list[i]);
    
    如果 i 的順序沒有關係, 下面是最快的方式:

i = sizeof(list);
while (i--)
    do_something_with_item(list[i]);
    
    這是所謂的 '基本狀況 while 迴圈'。和下面的迴圈或其他的 while
迴圈沒什麼不同, 但還是有少許利益。

for ( i = sizeof(list) ; i-- ; )   ;


3.2. FOR
    
    一個最常見的迴圈結構, 對在你每次都要在迴圈最後做一個複雜的狀況
運算較有用。如果只是簡單的指數增加或減少, 用`while'比較好。

    對於結束狀況就複雜的例子:

for ( initialise ; test ; final ) {
    main body
}

比以下`清楚'

initialise
while ( test ) {
    main body
    final
}
    

3.3. SWITCH

    在可許的情況下, 應用`switch' 敘述 instead of(shit..what's the
Chinese for instead???) `if-then-else-...'結構, switch 敘述需在 driver
內效率化。不論如何, 至少程式看起來比較乾淨。
    用 switch 的例一個優點是 `狀況範圍' 的支援(一個 C 沒有的特色)。
如果你的測試設定如下面的範圍:

case 1:  case 2:  case 3:

可用以下代替:

case 1..3:

可能較為有效率(至字少較好打)
