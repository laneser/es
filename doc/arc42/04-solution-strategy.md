# 04 解決策略

四個最根本的架構決定，它們解釋了這個 codebase 為什麼長這樣。

## 一、世界即物件圖

沒有資料庫。整個遊戲世界就是一堆互相持有參考的 LPC 物件，活在驅動的記憶體裡。
房間持有出口、身上的 NPC 與道具；角色持有裝備；裝備持有屬性。

持久化用的是驅動的 `save_object()`，把物件的變數序列化成純文字的 `.o` 檔
（副檔名剛好叫 `.o`，但**跟編譯產物毫無關係**）。發生在登入、登出、斷線、
手動 `save`、正常關機，以及每 `AUTOSAVE`（`<body.h>`，預設 23 分鐘）一次的
定時存檔。

> 定時存檔原本被註解掉，2026-09 才接回來。在那之前 driver 只要不是走正常
> 關機流程（`docker rm -f`、OOM、當機），玩家從登入到被砍為止打到的東西
> 全部不見。同時補上的還有 `/adm/daemons/snapshotd.c` —— 存檔本身只會被
> 蓋掉，它另外留一串可回溯的副本，詳見
> [08 橫切概念](08-crosscutting-concepts.md#存檔快照)。

代價是：**重開機等於世界重置**。房間裡的道具、地上的屍體、NPC 的血量
全部回到初始狀態。只有玩家角色會被還原回來。

## 二、屬性集中在一個 mapping

物件的狀態不是散落的成員變數，而是集中在兩個 mapping 裡
（`/std/object/prop.c`）：

```c
mapping ob_data;        // 會存檔
nosave mapping tmp_ob_data;   // 不存檔的暫時狀態
```

透過 `set()` / `query()` / `delete()` / `add()` 存取，支援 `"a/b/c"` 這種
巢狀路徑。詳見 [08 橫切概念](08-crosscutting-concepts.md)。

**為什麼這樣做**：因為巫師要在遊戲裡即時改物件。如果屬性是成員變數，
`update` 一個物件會讓所有既存實例的變數配置錯亂；集中在 mapping 裡，
新舊程式碼對同一份資料的解讀是一致的。存檔格式也因此天然向前相容 ——
新增一個屬性不需要改任何序列化程式碼。

## 三、程式碼即內容，巫師在遊戲裡開發

`/d/<領域>/` 底下的幾千個檔案既是程式也是內容。巫師登入之後可以：

- `ed` / `cat` 讀寫檔案（受權限管制）
- `update` 重新編譯載入單一物件
- `clone` / `goto` / `eval` 即時測試

這導致了兩個必然結果：

1. **必須有細緻的檔案權限系統**，否則巫師可以互相破壞。
   見 [08 橫切概念](08-crosscutting-concepts.md) 的 uid 章節。
2. **必須容忍執行期錯誤**。巫師一定會寫出壞掉的程式碼，系統要能
   只中止那一個呼叫鏈而不影響其他人。

## 四、虛擬物件：用一份樣板生出幾千個房間

`/d/` 底下約有 970 個檔案是「虛擬物件」—— 檔名以 `_` 開頭，
**不繼承任何東西**，只提供一個 `create(object ob)`，對傳進來的物件下設定。

驅動找不到 `foo.c` 時會問 master，master 轉給 `VIRTUAL_D`，
後者找到最近的 `<目錄>/virtual/server.c`，由它 `new(ROOM)` 出一個空房間、
呼叫 `_foo->create(那個房間)`、再把樣板檔 destruct 掉。

**為什麼**：省記憶體。1994 年的機器上，讓幾千個房間各自繼承一份完整的
room 程式碼是負擔不起的。同樣的動機也產生了 `compress_obj.h`
（clone 物件不自己存 `ob_data`，轉問 blueprint）。

代價是這個 lib 最容易踩的坑：**引用時寫不含底線的路徑，編輯時改有底線的檔**。
詳見 [08 橫切概念](08-crosscutting-concepts.md)。
