# 11 風險與技術債

依「會不會咬人」排序，不是依數量。

---

## 高：潛伏的驅動相容性地雷

這次升級抓到的四個執行期 bug 有共同模式：**舊驅動寬容、新驅動嚴格，
而且都不是語法問題，所以編譯期完全看不出來**。

| 已修的 | 舊驅動 | 新驅動 |
|---|---|---|
| `message()` 第 4 參數 | 傳 `0` = 不排除任何人 | 型別錯誤 |
| `userp(0)` | 靜靜回 `0` | 拋錯 |
| `__FILE__` in include | 最外層主檔案 | include 檔自己 |
| `tell_room()` varargs | 省略參數沒事 | 省略的 `0` 被傳下去就炸 |

**風險在於同類問題還散落在沒被執行到的程式碼裡。** 全樹掃描的實證：
`/d/` 底下 23 個領域、5951 個檔案，有 **20 處 `Bad argument 1 to EFUN call_other()`**
——那就是「對 0 做 call_other」，與 `userp(0)` 同源，只是還沒有人走到那段程式碼。

已知的具體數字：

- **約 178 個 `userp()` / `wizardp()` 呼叫點**沒有逐一檢查過空值防護。
  只修了 `/std/user.c` 裡的兩個。
- `varargs` 函式把「沒給的參數」當成 `0` 傳給嚴格的 efun ——
  這個模式在這個 codebase 裡很常見，只確認過 `tell_room`、`say`、`shout`。

**怎麼收斂**：見底下 [下一步](#下一步) 的第 1 項（巡邏員）。

---

## 高：`data/` 被 git 追蹤

644 個 `.o` 檔、6.9MB，包含帳號（密碼雜湊、email）與角色狀態。
它們是執行期產物，**跑過遊戲之後 `git status` 一定不乾淨**。

後果是每次 commit 都要確認沒有把測試痕跡送出去（連線 IP、last_on 時間戳、
自動升級後的密碼雜湊）。這在本次工作中實際發生過數次，靠 `git checkout -- data` 補救。

**沒有處理是刻意的決定**：保留 `data/` 讓 clone 下來就能照 README 登入
（`admin` / `12345`），而 `d/*/data/attic/` 底下是 1990 年代的留言板歷史，
有文物價值。代價就是上面那個摩擦。

如果哪天要處理，最小的動作是把 `data/backup/`（68 個孤兒備份，
對應的種族 `lizardman`、`hawkman` 連現役角色都沒有）移除並 gitignore。

## 中：死檔與殘骸

核心目錄 746 個檔案中有 32 個載入失敗，**絕大多數不是這次升級造成的**，
而是 inherit 早已不存在的檔案：

| 失效的引用 | 影響 |
|---|---|
| `/std/body/wild_card` | `/std/adt/body` |
| `/std/object/sec_ob` | `/std/cards/card` |
| `/cmds/std/_praise` | `idea`、`query`、`typo` 三個指令 |
| `/u/i/iris/races/iris` | `/std/user_ob/test`（某巫師家目錄早就刪了） |
| `/std/room`、`/std/map` | `grid_server`、`map_old` |

還有兩類更隱蔽的：

- **`/adm/simul_efun/` 底下有 5 個檔案沒被聚合檔 include**
  （`message.c`、`help.c`、`lines.c`、`cat.1208.c`、`data.1208.c`），
  改它們不會有任何效果。本次升級曾因此誤判過一次。
- **`/adm/daemons/network/` 整套 intermud 程式碼**是 1990 年代 MUD 互連的產物，
  對應的伺服器早就不存在，多數編譯失敗。

**沒有清理是刻意的**：分辨「死檔」與「暫時沒人用但還有價值」需要領域知識，
而原作者都聯絡不到了。誤刪的成本高於留著的成本。

## 中：全樹掃描的現況

`lest` 對整棵樹掃過一遍的結果（2026-09 升級後）：

| 範圍 | 檔案 | 載入失敗 | 成功率 |
|---|---|---|---|
| 核心（`/std`、`/cmds`、`/adm`、`/obj`） | 746 | 32 | 95.7% |
| `/d/` 全部 23 個領域 | 5951 | 177 | 97.0% |
| **合計** | **6697** | **209** | **96.9%** |

領域中失敗較多的：`noden` 66、`eastland` 46、`island` 17、`scholar` 9、`std` 8。
`deathland`（512 檔）、`healer`、`martial`、`thief`、`magic`、`knight`、`abyss`
等領域是 0 失敗。

**剩下的 209 個沒有大的共同根源了**——最多只有 3 個檔案指向同一個失效目標。
先前那種「修一個檔案救 33 個」（`ref_d`）或「修一種寫法救 234 個」
（include 角括號）的槓桿已經用完，往下就是逐檔處理。

## 中：測試覆蓋率極低

目前 51 個斷言，覆蓋 7 個檔案。分母是幾千個檔案。

但覆蓋率這個數字對這個 codebase 意義有限——`/d/` 底下幾千個房間描述檔
測不出什麼有價值的東西。比較有意義的問法是**「被大量複用的東西有沒有被保護」**：

| 已保護 | 未保護 |
|---|---|
| `ob_data` 屬性系統 | `/std/living.c`、`/std/npc.c` |
| `verify_password` | 戰鬥計算（`attack_d`、`combat_d`） |
| `tell_room` | `cmd_d` 的指令查找 |
| 武器、房間基底 | 虛擬物件生成（`virtual_d` 與各 `server.c`） |

`lest -u` 列出未覆蓋清單。

## 低：編碼殘留

- **`□`（U+25A1）缺字**：Big5→GBK 時代就遺失的字，例如
  `cmds/std/_look.c` 的「這□沒有任何明顯的出口」。**無法自動修復**，
  每一個都要人依上下文猜出原字。
- **27 處行尾續行型、59 處雙反斜線型**的殘留反斜線語意不明確，保留未動。
  搜尋方式：`grep -rP '[\x{4e00}-\x{9fff}]\\\\$'`
- `data/attic/` 16 個檔含 U+FFFD，來源是原檔本身的壞位元組。

---

## 低：編譯警告

全站掃描累積約 1300 則警告，其中：

| 警告 | 數量 | 要不要管 |
|---|---|---|
| `Unused local variable` | ~1143 | **不建議大掃除**。這個 lib 有大量被 `/* */` 註解掉的程式碼，變數往往是為那些程式碼宣告的 |
| `Redeclaration of global variable` | ~111 | **值得看**。inherit 鏈裡同名全域變數重複宣告，行為可能不是預期的 |
| `/* found in comment` | 16 | **值得看**。巢狀註解可能意外吃掉一段程式碼 |
| `Illegal to redefine function` | 6 | 值得看 |
| `Illegal to inherit after defining global variables` | 2 | 值得看 |

## 下一步

前面幾節描述的是**現況**，這一節是**待辦**，按投報率排序。

---

### 1. 寫一個「巡邏員」，逼出剩餘的執行期地雷

**為什麼排第一**　這是唯一能系統性收斂前面「潛伏的驅動相容性地雷」那一節的辦法。
現況是已知至少 20 處 `call_other(0)` 與約 178 個未檢查空值的
`userp()`/`wizardp()` 躺在沒被執行到的程式碼裡，而 `lest` 的第一層
（`load_object`）永遠抓不到它們 —— 那些程式碼在語法與型別上完全合法，
要等真的執行到那一行、參數真的是 `0` 時才會炸。

這次升級真正咬人的四個 bug 全是這一類，而抓到它們的方式是「有人登入、
走一走、死一死」。那是有效的，但不成系統：玩家走過的路徑是隨機的，
而且會集中在熱門區域。

**怎麼做**　`/adm/daemons/lest_d.c` 已經有現成的骨架可以改：
遞迴收集路徑、`call_out` 分批（避開 eval cost 上限）、寫 log、
可查詢進度。巡邏員要做的是把「`load_object()` 一遍」換成實際互動：

- 每個房間：`look`、逐一走過 `exits`、檢視 `item_desc`
- 每個 NPC：clone 出來、`look`、觸發一次戰鬥回合、`die()`
- 每個物品：clone 出來、`query()` 常見屬性、`move()` 進出容器

然後蒐集 `log/debug.log` 的「執行時段錯誤」並依錯誤訊息分類 ——
這次升級的經驗是**同一類錯誤往往有共同根源**，分類比逐條看有效得多。

**注意**　互動比載入的副作用大得多（NPC 會死、物品會被 destruct、
房間狀態會變）。一定要在測試環境跑，而且跑完最好重啟 driver。
戰鬥與死亡流程會觸發 `heart_beat`，所以巡邏員不能在單一 tick 裡做完，
必須分批並讓出時間給心跳。

---

### 2. 補 `/std/living.c`、`attack_d`、`cmd_d` 的 spec

**為什麼排第二**　[10 品質與測試](10-quality-and-testing.md) 的「已保護／未保護」
表格裡，未保護那一欄有三個東西被大量複用，而且邏輯複雜到值得測：

| 目標 | 為什麼值得 |
|---|---|
| `/std/living.c` | 所有玩家與 NPC 的共同基底，`/std/user.c` 和 `/std/npc.c` 都從它來 |
| 戰鬥計算（`attack_d`、`combat_d`） | 遊戲規則的核心，改動的回歸風險最高，目前零測試 |
| `cmd_d` 的指令查找 | 每個玩家的每個指令都經過它；`rehash` 與 `PATH` 的交互是常見困惑來源 |

相對地，`/d/` 底下幾千個房間描述檔不值得寫 spec ——
測「這個房間的 long 是不是這串字」沒有意義。

**怎麼做**　`lest -u` 列出未覆蓋清單。寫法見
[10 品質與測試](10-quality-and-testing.md)，現成範本是
`/std/object/ob.spec.c`（純邏輯）與 `/std/room/room.spec.c`（需要受測物件）。
戰鬥計算比較麻煩，需要在 spec 裡自己 clone 出攻守雙方，
`lest_subject()` 可以回傳其中一方，另一方在 `test_` 函式裡建。

---

### 3. 逐檔清理那 209 個載入失敗

**為什麼排最後**　投報率已經和前兩輪完全不同。先前「修 `ref_d` 一個檔案救 33 個」、
「修 include 寫法救 234 個」那種槓桿已經用完 —— 現在最多只有 3 個檔案
指向同一個失效目標，等於逐檔處理。

而且**多數不是修，是判斷要不要刪**。它們大多是 inherit 早已不存在的檔案
（`/std/body/wild_card`、`/cmds/std/_praise`、`/u/i/iris/races/iris`），
1990 年代就壞了，不是這次升級造成的。

**難處在於分辨「死檔」與「暫時沒人用但還有價值」**，而這需要領域知識，
原作者又都聯絡不到。誤刪的成本高於留著的成本，所以這件事的正確做法
不是「清乾淨」，而是**逐一判斷並留下判斷紀錄**。

**怎麼做**　從 `lest` 的報告取清單，依失效目標分組（同一個缺失檔案影響哪些檔），
對每一組回答：這個功能現在還走得到嗎？有沒有替代品？
判斷結果寫進這份文件，而不是只是刪掉。

## 結構性風險（不打算處理，但要知道）

- **重開機等於世界重置。** 只有玩家角色會被還原，房間狀態、地上的東西全部重來。
- **沒有備份機制。** `data/` 的保護全靠 git。
- **單點故障。** 一個程序、一個執行緒。任何一段 LPC 跑太久都會卡住所有人，
  只有 eval cost 上限這道保險。
- **沒有原作者可問。** 檔頭的修改紀錄是唯一的口述歷史。
